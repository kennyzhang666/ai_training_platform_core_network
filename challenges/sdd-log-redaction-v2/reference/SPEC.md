# 运维日志脱敏工具规格 v2.0

## 目标与非目标

目标是为运维批量日志提供确定、幂等、可审计的逐行脱敏能力。工具必须在保留排障所需结构、Unicode 和非敏感类型的同时，清除凭据、个人标识与网络标识；对需要跨记录关联的字段生成不可逆的稳定别名；对无法安全判断的结构化输入执行失败关闭。

非目标包括解析任意二进制格式、连接在线数据分类服务、保存原始日志、提供密钥管理系统，以及对自然语言中的姓名和地址进行概率识别。本实现不承诺修复上游日志格式，只输出脱敏内容或稳定错误标记。

利益相关方包括运维、隐私、审计和安全团队。运维要求结构与关联可用；隐私要求敏感值不可恢复；审计要求规则版本和判定可复现；安全要求密钥、错误日志和异常路径不产生二次泄露。

## 范围、约束与威胁边界

范围是 UTF-8 行式文本文件，其中每行是普通文本、JSON 对象或 JSON 数组。Python 版本固定为 3.11，只允许标准库，不访问网络。处理以单行为事务边界，不跨行拼接 JSON。

威胁边界包括：日志值可能包含口令、令牌、身份号码和伪造结构；攻击者可能构造畸形 JSON 或超长行；低熵员工编号可能被无密钥散列反推；异常堆栈可能复制原文。运行主机和注入密钥的运维流程位于信任边界内，输入日志不可信。

资源约束为最大行长由策略 `maxLineChars` 声明，默认 4096 字符；输入必须逐行迭代，禁止 `read()` 或 `readlines()` 一次性占用内存；2000 行基准应在 5 秒处理时限内完成。实现不得记录原文，也不得把 HMAC 密钥、测试凭据或真实员工数据写入交付件。

## 关键假设、歧义与决策记录

关键假设 A1：同一批次使用同一密钥，批次间可轮换密钥。歧义是“关联可用”是否允许跨赛季复用；确认结论为只保证同一密钥域内稳定，不保证跨密钥域一致。

关键假设 A2：字段名比较不区分大小写，并把连字符统一为下划线。决策记录 D1：结构化字段分类优先于值内正则，防止数字口令因类型不同而漏脱敏。

关键假设 A3：以 `{` 或 `[` 开头的行被声明为结构化输入。决策记录 D2：解析失败返回 `MALFORMED_JSON`，不得降级为普通文本，因为部分正则替换不能证明原文已安全。

决策记录 D3：身份证号规则优先于手机号，授权头与 URL 密钥参数优先于一般键值规则，已生成的掩码和 `hmac:` 别名不得再次变换。

## 数据分类与规则优先级

敏感字段集合包括 `authorization`、`password`、`token`、`access_token`、`api_key` 和 `secret`，结构化日志中无论原值是字符串、数值、布尔还是空值，一律输出字符串 `***`。关联字段集合包括 `user_id` 和 `device_id`，原值转换为字符串后计算 HMAC-SHA256，输出 `hmac:` 加前 24 位十六进制摘要。

普通文本规则覆盖 Authorization、URL 查询密钥、键值密钥、关联标识、身份证号、手机号、邮箱、IPv4 和 MAC。规则优先级严格遵循策略 `textRulePriority`：授权头 → URL 查询密钥 → 键值密钥 → 关联标识 → 身份证号 → 手机号 → 邮箱 → IPv4 → MAC。此顺序避免身份证片段被手机号规则先消费，也避免 URL 值被普通键值规则扩大匹配范围。

手机号保留前三后四，身份证号保留前六后四，邮箱仅保留本地部分首字符和域名，IPv4 保留前两段，MAC 保留前两段。凭据类值全部替换为 `***`，不得保留长度或前后缀。

## 策略契约

策略文件固定为 `policy/redaction_policy.json`，必须包含 `version`、`maxLineChars`、`keyEnv`、`secretFields`、`correlationFields` 和 `textRulePriority`。规则版本为 `2.0`；密钥环境变量固定为 `LOG_REDACTION_KEY`；最大行长允许 16 到 1048576。缺字段、类型错误、未知优先级顺序或越界值均判定为 `POLICY_INVALID`。

HMAC-SHA256 密钥不得写入代码、策略、README、测试或日志。公开函数允许测试通过 `key` 参数注入；生产命令行只能从 `keyEnv` 声明的环境变量读取。只有处理关联字段时才要求密钥；密钥少于 16 字节、为空或缺失时均抛出 `KEY_UNAVAILABLE`。

## 输入输出契约

`load_policy(path)` 输入是策略路径，期望输出为已校验的映射；失败仅包含 `POLICY_INVALID`。

`redact_line(line, policy=None, key=None)` 输入是不含行尾符的字符串，期望输出是单行脱敏字符串。普通文本保持非敏感字符次序；JSON 使用 `ensure_ascii=False`、稳定键序和紧凑分隔符。以 `{` 或 `[` 开头但解析失败时输出 `[REDACTION_ERROR:MALFORMED_JSON]`；超过最大行长时输出 `[REDACTION_ERROR:LINE_TOO_LONG]`。

`redact_stream(reader, writer, policy=None, key=None)` 输入是可迭代行读取器和文本写入器，期望输出为 `lines`、`redacted`、`errors` 三项整数统计。每个输入元素只处理一次，每个输出元素以单个换行结束。`redacted` 统计内容发生变化或被错误标记的行，`errors` 统计 `[REDACTION_ERROR:` 开头的行。

命令行输入参数为 `--input`、`--output`、`--policy`。输出必须先写同目录临时文件，全部完成后原子替换目标；中途失败必须删除临时文件，不能留下部分结果。成功判定为退出码 0；策略、密钥或文件失败判定为退出码 2，标准错误只允许 `ERROR <稳定错误码>`。

## 组件设计

策略组件负责 `load_policy` 与 `validate_policy`；密钥组件负责环境读取和 HMAC 别名；文本组件按冻结优先级执行确定性正则；结构组件递归处理映射和数组；单行组件区分普通文本与结构化输入；流式组件迭代输入并累计统计；命令组件管理临时文件、原子替换和退出码。

所有组件共享同一已校验策略。结构组件先按字段名分类，再递归处理一般值；文本组件不解析 JSON。此边界保证规则更改的影响范围可定位，也避免普通文本逻辑意外改变 JSON 数值、布尔和空值类型。

## 失败策略与错误码

总体失败策略是失败关闭：无法证明脱敏完整时不得回显原文，不得把输入拼入异常、标准错误或测试报告。稳定错误码如下：

| 错误码 | 条件 | 单行输出或进程行为 |
| --- | --- | --- |
| `KEY_UNAVAILABLE` | 关联字段需要 HMAC 但无有效密钥 | API 抛错；CLI 退出 2 |
| `MALFORMED_JSON` | 声明为结构化输入但 JSON 解析失败 | 固定错误标记，继续下一行 |
| `LINE_TOO_LONG` | 字符数超过策略上限 | 固定错误标记，继续下一行 |
| `POLICY_INVALID` | 策略缺字段、类型或顺序错误 | 加载失败；CLI 退出 2 |
| `IO_ERROR` | 文件读写失败 | CLI 退出 2 |

诊断只保留稳定错误码和聚合计数，不得回显原文、密钥、期望值或异常堆栈。畸形 JSON 不做“尽力正则替换”，因为未识别片段可能继续包含敏感信息。

## 数据保真与幂等

JSON 的对象、数组、数值、布尔和空值语义保持不变，只有敏感字段值被固定替换，字符串内容执行文本规则。Unicode 使用 UTF-8 读写并设置 `ensure_ascii=False`，中文等非 ASCII 字符不转义。

掩码输出不再匹配原始规则；`hmac:<24 hex>` 被识别为已处理别名。因此相同策略与密钥下，对输出再次调用 `redact_line` 必须逐字相同。同一原值与同一密钥产生同一别名，不同原值或不同密钥产生不同别名。

## 验收标准

- AC-01：输入普通文本同时包含手机号、身份证、邮箱、IPv4 和 token，期望输出逐类脱敏且找不到任一原值；判定由 `test_plain_text` 与 HT-01 通过。
- AC-02：输入含嵌套对象和数组的 JSON，期望输出敏感字符串已替换且数值、布尔、空值类型不变；判定由 `test_nested_json`、HT-02、HT-03 通过。
- AC-03：输入大小写不同的口令和授权字段，期望输出值均为 `***`；判定由 HT-04 通过。
- AC-04：输入 Authorization 头和带密钥参数的 URL，期望输出只替换凭据参数；判定由 `test_url_and_authorization` 与 HT-05 通过。
- AC-05：输入重叠身份证号与手机号，期望输出按身份证优先级分别掩码；判定由 `test_rule_priority` 与 HT-07 通过。
- AC-06：输入同一关联值两次，期望输出相同 HMAC 别名；更换值或密钥后输出不同；判定由 `test_hmac_correlation`、HT-09、HT-10 通过。
- AC-07：输入已脱敏输出，期望输出逐字不变；判定由 `test_idempotent` 与 HT-08 通过。
- AC-08：输入 Unicode、畸形 JSON 和超长行，期望输出分别保真或固定错误标记；判定由 `test_unicode`、`test_malformed_json`、`test_line_too_long` 与 HT-11、HT-14、HT-15 通过。
- AC-09：输入无效策略或缺失密钥，期望输出稳定错误码且不含原文；判定由 `test_invalid_policy`、`test_missing_key` 与 HT-13、HT-16、HT-18 通过。
- AC-10：输入禁止批量读取的单次迭代器，期望输出完整且无 `read()` 调用；判定由 `test_streaming`、HT-19、HT-20 通过。
- AC-11：输入 2000 行混合日志，期望输出 2000 行、统计一致并满足处理时限；判定由 HT-21、HT-22 通过。
- AC-12：输入变更后的 `maxLineChars` 策略和处理到中途才发现缺密钥的 CLI 场景，期望输出使用新上限，失败时不留下部分目标文件；判定由 HT-23、HT-24 通过。

## 可观测性与审计

本地 API 返回聚合统计，不打印逐行内容。平台评测只记录隐藏用例编号、层级、通过数量、评分点和稳定诊断码，不记录隐藏输入、期望输出或完整源码。审计可依据策略版本、提交快照、引擎版本和测试编号复现结论。

运行日志允许记录开始时间、结束时间、总行数、变更行数、错误行数和进程退出码。任何采样、调试原文和密钥指纹都不在允许范围内。

## 变更影响与回滚

规则版本 `2.0` 冻结字段分类、优先级、错误码和公开接口。补充新的字段别名可在保持已有结果不变时向后兼容；调整掩码、优先级、HMAC 长度或错误语义属于破坏性变更，必须发布新规则版本。

影响范围至少覆盖策略、实现、测试、SPEC、README 和运行配置。变更前建立对照样本，变更后执行公开全量测试与平台验收，并比较非敏感字段、错误计数和关联稳定性。

回滚步骤：停止新批次；恢复上一规则版本的策略和匹配实现；恢复对应密钥域配置；重新执行公开测试与平台参考验收；确认输出格式和统计恢复后再开放处理。回滚验证包括 `unittest`、语法检查、参考交付件 24/24 和至少一份历史脱敏快照的非敏感语义比较。
