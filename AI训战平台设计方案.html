01方案概览

要解决的三个问题

怎么练

新人不缺 AI 工具，缺的是在约束下把 AI 用出确定结果的方法。 训战用真题 + 隐藏验收 + 中途变更来逼出这套方法。

怎么测

「AI 用得好」过去只能靠主观印象。本方案把它拆成 16 个有明确判据的得分点，其中 14 个由脚本或结构化抽取自动定档。

怎么比

蓝黄各自出题、各自评比，单场只在同区同题内排名， 天然公平。赛季榜用场次百分位折算积分，两区场次尺度一致。

一句话方案

黄区部署唯一一套系统，承载题库、领题、评测、成绩与能力画像； 学员在内部 GitLab 各自分支上作业，push 即触发 GitLab CI 自动评测。 蓝区零部署：GitHub 建题库仓，学员提交后由 Claude / Codex 按同一套评测标准出结果 JSON，上传黄区统一展示。

两区共用同一套维度骨架与结果 Schema，差异只落在一份阈值配置里—— 判据方向甚至可以相反（强模型下迭代 12 轮是没说清，弱模型下迭代 12 轮是拆得好），但输出结构完全一致， 所以一套展示层能吃两边数据——这是「只有一个总赛季榜」的前提： 两区的分若不是同一尺度的东西，赛季榜根本加不起来。

与常规「刷题平台」的三点不同

维度常规做法本方案
评什么测试通过率 测试只占 40 分。另外 60 分测的是过程：规格写没写清、代码抗不抗变更、跟 AI 怎么协作的
怎么评主观项人工打分，或让大模型自由评分 拆成一串是否抽取 + 必须引用原文，引用由程序校验真伪，分数由算术汇总。 弱模型也能可靠执行，且同一份提交重跑必然同分
怎么用分数排名、发奖 排名之外，每次提交产出完整评测报告（四维度图表 + 逐条判据 + 扣分证据链）， 个人侧沉淀能力画像与赛季趋势；出题侧顺带产出模型基准库服务选型

02三维正交模型

平台里一切东西的组合都由三个互不耦合的维度决定。这一点必须在数据模型层面守住， 否则「蓝区的团队赛季项目」这种组合会退化成一堆 if-else。

分区

蓝区 / 黄区

决定：用哪份阈值 profile、哪个评测执行体（CI 还是 Claude）、 可用工具链与模型。不决定维度骨架与 Schema。

项目类型

个人 / 团队

决定：成绩归属主体、排行榜口径、分支命名规则。 个人项目归到人，团队项目归到组并在组内展示各成员的 commit 贡献。

赛制

集中场次 / 开放窗口 / 赛季

决定：评测何时触发、结果何时可见。 赛季是容器，装若干前两种项目并做汇总。

赛制的技术差异只有一个开关

赛制评测触发结果可见典型用法
集中场次push 即跑 封存，到点由管理员一键揭晓团队集中训战，半天一场，当场出榜复盘
开放窗口push 即跑 即时，几分钟内可见完整报告个人刷题，题目开放一到两周，自行安排

2.4 组织层级与作用域

平台后续会有多个部门使用，所以组织结构不能写死。设计成可配置层级的组织树 + 向下继承的作用域： 一道 4 级部门发布的题，5 级、6 级的人全都能参加。

层级标签可配置

层级数量与每级的叫法都是配置项，换个组织换套标签即可，不改代码：

orgLevels:
  - { level: 1, label: "BG" }
  - { level: 2, label: "产品线" }
  - { level: 3, label: "部门" }
  - { level: 4, label: "分部" }
  - { level: 5, label: "科室" }
  - { level: 6, label: "组" }

作用域用物化路径实现

每个组织节点带一条物化路径，员工和题目都挂在某个节点上。 可见性判定退化成一次字符串前缀匹配，索引友好、查询极快：

组织节点   /1/12/125/1251/           分组核心网控制开发部（4 级）
员工归属   /1/12/125/1251/1251A/     该部下面某个 5 级科室的人
题目归属   /1/12/125/1251/           发布在 4 级部门

可参加  ⟺  employee.orgPath.startsWith(challenge.orgPath)

向下继承

题目发布在哪一级，该级及其全部后代都自动纳入。 4 级部门出的题，下面所有 5 级、6 级不用重复配置，也不会漏人。 发布在 2 级产品线的题，整条产品线都能打。

不向上、不横向

上级看不到下级的私有题，兄弟部门之间互不可见。 要跨部门共享，把题目上提到共同祖先节点发布即可—— 这也是「公共题库」的实现方式：挂在最顶层节点上。

榜单口径：默认全域，支持下钻

一道 4 级部门的题被 5 级、6 级的人一起做，榜单怎么排？ 默认所有参与者同榜（同题同分区，本来就公平），同时提供组织维度的筛选：

榜单视角范围典型用法
全域榜该题所有参与者默认视角，看自己在整个可参与范围内的位置
本级榜与我同一节点的人看自己在本组/本科室内的位置，压力更可控
下钻榜指定任一子节点管理者查看某个下级单位的整体表现

赛季榜同理，可在我的组 / 我的部 / 全域之间切换。 个人的赛季积分只算一次，变的只是排名参照系。

角色可操作范围

03架构与数据流

核心约束是网络策略：黄区可 clone GitHub，不可 push；蓝→黄小数据摆渡分钟级。 数据因此只能单向流动，全量视图只能在黄区。这不是设计取舍，是策略推导出的必然结果。

关键设计取舍

取舍选择理由
蓝区要不要部署不部署 学员是同一批人、本来就能上黄区看成绩。蓝区只需要一个 GitHub 仓 + 一份评测指令，省掉一整套部署与运维
评测跑在哪GitLab CI push 即触发，开放窗口的「随时刷榜」才成立。手动评分撑不住持续提交
沙箱怎么做K8s Job + 无网络 + 只读挂载 + 超时 学员代码必须隔离执行。容器天然解决隔离与并发
蓝区结果怎么进来上传 JSON，非摆渡代码 几 KB、无代码内容，审批阻力最小；代码留在蓝区，合规最干净
题面怎么同步黄区 clone GitHub 题面与 starter 无密级，蓝区维护一份，黄区拉取即可，避免两处维护

3.1 蓝区：集中收卷、批量一次评

蓝区只做集中限时赛，没有刷榜。这让整个蓝区流程退化成一次性批处理—— 不需要 CI、不需要即时反馈、不需要并发调度：

步骤时机动作
1赛前GitHub 建题库仓，为每人/每组开分支，下发地址
2赛中学员用 DeepSeek / Claude / Codex 作业并 push
3到点收卷：锁定分支（设 protected 或记录截止 commit）
4评测用 Claude / Codex 跑批量评测指令，一次评完全场
5校验Schema 校验 + 分值加总核对，不通过则重评
6上传结果 JSON 传入黄区平台，统一揭晓

批量评分反而比逐份评更稳

这是一次性集中评分带来的额外好处：评测模型同时看得到全场所有提交， 可以先通读一遍建立本场的相对基准，再逐份定档。相比逐份独立评分， 横向参照能显著压住「同一份材料评两次差好几分」的抖动。

建议再加一道保险：同一批评两遍， 把两遍档位不一致的得分点挑出来人工确认。全场十几份提交，不一致项通常只有个位数， 成本很低但把一致性钉死了。

客观底座仍然必须真跑——隐藏测试要让评测模型实际执行代码拿到通过情况，不能靠读代码推断。 主观项仍然走 4.4 的结构化抽取，与黄区同法。

04评测体系

这是整个方案最核心的部分。设计目标只有一句：同样的提交，谁来跑、跑几次，都是同一个分数； 每一分的扣减都能指到具体位置。

D 未做到0魔法数字 > 5 处，或完全没有常量抽取

「业务魔法数字」的精确定义：出现在函数体内的数值字面量，排除 ①模块级常量定义中的字面量；②作用在具名常量上的单位换算因子（FREE_MINUTES * 60 里的 60 不算）； ③通用中性值（0、1、-1、2）。该定义在三种语言上用同一套 tree-sitter 查询实现。

产出证据：每一处魔法数字生成一条 finding，含文件、行号、代码片段、为什么错、怎么改。 学员对分数有异议时，逐条对即可。

4.3 分区差异：同骨架、不同阈值

「分区不同评测也不同」的正确实现方式，不是换维度，是换阈值。 一旦换维度骨架，就要维护两套报告模板、两套能力画像， 而且赛季榜没法合并——个人画像也无法跨场次累积。

差异呈现出一个清晰的梯度——越靠近客观产出，两区越一致；越靠近人的行为，差异越大：

交付验证
完全一致 代码质量
几乎一致 规格质量
阈值不同 协作过程
判据方向可以相反

条形长度表示两区判据的差异程度。测代码好坏与用什么模型无关，测人怎么跟模型协作则完全取决于模型强弱。

差异最大的两个得分点

4.4 结构化抽取阅卷法

这是整个评测体系里技术含量最高的一环，解决的问题是：如何让弱模型可靠地评价主观项。

❌ 直接打分（不可用）

阅读这段对话记录，
给提示词质量打 0–10 分。

同一份材料跑两次能差 3 分。弱模型没有稳定的综合判断力， 强模型也会因温度和上下文漂移。这种分数进不了任何正式口径。

✓ 拆成客观抽取（可用）

X1 学员有没有要求 AI 复述理解？
    yes / no / unclear
    答 yes 必须逐字引用原文

二元判断 + 强制引用。弱模型能可靠执行， 分数由算术汇总而非模型给出，重跑必然同分。

防幻觉的关键：引用可程序校验

要求模型答 yes 时必须逐字引用原文，然后由程序把这段引用拿回原始对话记录里做精确匹配：

  • 匹配上 → quoteVerified: true，该抽取项生效
  • 匹配不上 → 判定为模型幻觉，该项自动按 no 处理，并进入人工复核队列

这一条把「相信模型」变成了「验证模型」。弱模型编造出来的证据会被自动拦下， 而且拦截率本身就是一个可观测的模型质量指标——顺带回答了「内部模型到底行不行」。

展开：黄区抽取 skill 的完整指令由 Claude 产出，装进黄区给内部模型跑 
你是训战评测的抽取助手。你的任务不是打分，是从对话记录里找证据。

【硬性规则】
1. 每题只能答 yes / no / unclear，不要给分数，不要评价，不要建议
2. 答 yes 必须附一段逐字引用（≤50 字），引用必须一字不差地出现在原文中
3. 找不到明确证据一律答 no。禁止推测、禁止脑补、禁止"可能"
4. 严格按 JSON 输出，不要任何额外文字

【抽取项 · 黄区】
Y1 学员有没有把任务拆成多个可以独立验证的小步骤？
Y2 学员在每个新步骤里，有没有重新补充必要的上下文（而不是假设模型还记得）？
Y3 学员有没有在步骤之间做验证（跑测试 / 让模型自查 / 人工确认）再继续？
Y4 出现错误时，学员是回退并重新拆解，还是用同一个提示词反复重试？
   → 回退重拆答 yes，反复重试答 no，无错误答 unclear

【输出格式】
{"Y1":{"a":"yes","quote":"我们先只做第一步：解析入参并校验"},
 "Y2":{"a":"no","quote":""},
 "Y3":{"a":"yes","quote":"跑一下测试再继续"},
 "Y4":{"a":"unclear","quote":""}}

为什么这套指令弱模型能跑：没有开放式判断，没有打分，没有多步推理。 每一题都是「在一段文本里找有没有某个东西」——这是弱模型最擅长的抽取任务， 而不是它最不擅长的综合评价任务。

汇总规则（确定性）：P3 得分 = 命中项数映射档位。 4 项全 yes → A（4 分）；3 项 → B（3 分）；2 项 → C（1.5 分）；≤1 项 → D（0 分）。 unclear 按 no 计。

蓝区用同一套方法

蓝区由 Claude / Codex 评测，能力远超需求，但仍然必须用结构化抽取—— 不是因为 Claude 做不了综合判断，而是因为只有两边用同一种评法，分数才可比。 让 Claude 自由打分，同一份提交评两次可能差好几分。 赛季榜把两区的场次积分加在一起，蓝区一抖，整个赛季榜的公信力就跟着抖。

一个值得写进教材的副产品：为了迁就弱模型而被迫发明的严谨方法， 用在强模型上同样让结果更稳。约束不是能力的对立面，约束是可靠性的来源。 这句话正是整个训战想让新人带走的东西。

打分规则的唯一载体是一个 skill

蓝区的执行体不固定——可能是 Claude、Codex，也可能是 opencode + DeepSeek。不同模型的综合判断力差异很大，如果打分规则只存在于 「给评测模型的一段提示词」里，分数会随执行体漂移。

所以把整套打分规则封装成一个 skill： 判据、抽取项、脚本、输出 Schema 全在里面。任何执行体都跑同一个 skill， 模型只负责第 5 步的抽取，分数由脚本按写死的判据算—— 这就是为什么换 Claude、换 Codex、换 DeepSeek，同一份提交的分数完全一致。

skill 内容作用

references/extraction.md蓝黄两套抽取项原文与输出格式
references/schema.md输出 Schema 与字段含义

黄区 CI 直接调用同一套脚本，与蓝区共用 rubric.md 判据。 一份规则、两处执行、结果同构——这是赛季榜能把两区场次加在一起的技术前提。

人工复核：从「打分」降级为「确认」

复核台只呈现被标为 yes 且 quoteVerified: true 的抽取项，导师做的事只有一件： 看这段引用是否真的支持这个结论。不支持就点掉，分数自动重算。 工作量从「读完整对话记录并打分」降到「看几条引用」——按 30 人一批估算，从数小时降到 20 分钟以内。

4.5 多语言公平性

题目有两种语言策略：限定单一语言（所有人用同一种，便于横向比代码）与 语言不限（Go / Java / Python 任选，贴近真实）。后者引入一个必须处理的问题： 选什么语言不能影响分数。

指标跨语言处理方式
验收测试通过率可比 同一批用例，每种语言各实现一套断言，题号与档位严格一一对应
圈复杂度 / 嵌套深度可比分支节点计数，三种语言语义一致
业务魔法数字可比字面量计数，与语言无关
显式抛错需语义映射 Go 不用异常。映射为：Python raise / Java throw / Go return err + errors.New
静默兜底需语义映射 Python .get(k, default) / Java getOrDefault / Go 忽略 error（_ = f()）
常量抽取数量需归一化 不比绝对值。按该语言参考实现的常量数做基准，取比值
代码行数 / 注释占比不可比 Java 天生冗长。只展示，不计分

硬规则：进入评分的指标必须跨语言可比或已归一化，不可比的只展示不计分。 出题时必须为每种允许的语言各准备一套隐藏测试与一份参考实现——这是语言不限带来的真实成本， 在出题工作量里要算进去（见 6.4）。

附带收益：语言不限的题目会产生一份「不同语言下 AI 辅助效果」的横向数据。 如果发现内部模型在 Go 上明显弱于 Python，这对部门技术选型与模型采购都是直接有用的输入。

4.6 模型基准库

学员比赛蓝归蓝、黄归黄，两区不同题、不跨区比分数。 但「内部模型到底比外部差多少」这个问题仍然需要答案——把它挪到出题环节去解决， 完全不碰学员比赛。

做法：出题体检时双模型裸跑

新题上架前本来就要用强模型裸跑一遍，验证澄清点埋得够不够深（见 6.6 自动体检）。 只要同时再用内部弱模型裸跑一遍，这道题就自带一组「同题、同隐藏测试、不同模型」的对比数据。

  • 零额外成本——数据是出题时顺带产生的
  • 不涉及任何学员——纯模型对模型，不违反两区不比的原则
  • 题库越大数据越厚，而且全部来自你们自己的真实任务，比任何公开 benchmark 都有说服力

4.7 CI 评测流水线

stages: [validate, prepare, verify, measure, extract, score, publish]

validate  提交契约校验（见 4.9）· 不合规立即产出诊断报告
prepare   拉取提交 · 识别语言 · 准备沙箱镜像
verify    K8s Job 跑隐藏测试（无网络 · 只读挂载 · 60s 超时 · 内存上限）
measure   tree-sitter 解析 → 跨语言度量 → 生成 findings
extract   调内部模型网关做结构化抽取 → 引用精确匹配校验 → 标记 quoteVerified
score     套分区 profile 逐点定档 → 汇总四维度 → 产出统一 Schema JSON
publish   写回平台 API；按赛制决定 reveal: immediate | on_release

安全

学员代码在 K8s Job 中执行：禁网、只读根、非 root、CPU/内存配额、硬超时。 评测容器与平台服务网络隔离。

并发

集中场次会出现几十人同时 push。用 CI 并发上限 + 队列， 保证最慢一份也在几分钟内出结果；不足则临时扩 runner。

幂等

同一 commit 重跑必须同分。抽取环节把模型温度设为 0， 并缓存 (commit, rubricVersion) 的结果。

4.8 无标准答案的挑战题

老员工发布的业务难题有两种：悬赏型（自己也没解决，发出来求解）与 探索型（「用 AI 到底能不能做成这件事」）。两种都没有隐藏测试可跑。 但这不意味着评测体系失效——

关键发现：四个维度里只有一个需要替换

Spec 25 / Code 20 / Collab 15 这 60 分测的是 「规格写没写清」「代码抗不抗变更」「跟 AI 怎么协作的」——这三件事都不需要标准答案， 结构扫描、AST 度量、commit 行为分析照跑不误。真正失效的只有 Verify 40 分。

因此把 Verify 做成可替换插槽，三种实现共用同一个 Schema：

题型Verify 40 分的实现判定方
test
标准题		隐藏验收测试四档加权脚本
bounty
悬赏题		出题人验收：解决程度四档出题人
explore
探索题		结论可信度：证据充分性四档出题人 + 复核

bounty 悬赏题四档

A 40完全解决，出题人确认可直接采用
B 28主要问题解决，遗留次要问题
C 16未解决，但提供了有效思路或缩小了问题范围
D 0无实质进展

explore 探索题四档

A 40给出可复现的验证（脚本/数据/步骤），结论有证据支撑
B 28有实验数据但不完整，结论方向可信
C 16仅定性判断，无可复现验证
D 0无依据的主观结论

Schema 完全不变：只是 verifyDetail 的内部结构不同、criteria 换一组 key、 source 标为 human。展示层、能力画像、赛季汇总一行代码都不用改。

榜单怎么算：自动评的进画像，人评的进荣誉

悬赏题的 40 分由人判，出题人有宽有严，直接混进赛季总分会污染可比性。建议分开：

榜单计入什么排序依据
赛季总分榜只算部门安排的官方项目 场次百分位积分累加。众包发布的题无论什么类型都不计入
挑战榜全部众包题（悬赏 / 探索 / 老员工标准题） 按被采纳数排，不按分数排。解决一个真实难题的荣誉，本来就比分数有意义
个人能力画像全部题目的 Spec / Code / Collab 这 60 分是自动评的、跨题型可比，不因 Verify 换了实现就丢掉

真实业务代码的权限边界

黄区允许挑战题直接使用真实业务代码与场景，但题目元数据必须声明 requiredRepos， 管理员在终审时一并授权。参与者的访问范围仅限声明的仓库，不做扩大授权。 敏感信息（客户名、IP、密钥、工号）由发布前的自动扫描拦截，见 6.6。

4.9 提交契约与格式校验

自动评测能成立的前提是交上来的东西长什么样是约定死的。 目录结构、必交文件、入口签名各交各的，评测引擎连要评的文件都找不到。 所以每道题都必须声明一份提交契约，平台在评测前先校验。

契约写在题目元信息里

submission:
  required:
    - path: SPEC.md
      type: markdown
      minSections: 7          # 七节模板必须都在
      notTemplate: true       # 不能原样交回模板（比对模板哈希）
    - path: transcript.md
      type: markdown
      minChars: 200
    - path: "{entry}"         # 按语言展开，见下
      type: source
      mustExport: calculate_fee
      signature: "(entry_time, exit_time, is_member=False)"
  optional:
    - path: tests/            # 自己写的测试，影响 S2 得分
    - path: NOTES.md          # 复盘与遗留问题
  forbidden:
    - "**/.env"
    - "**/*credential*"
    - "hidden_*"              # 不许提交隐藏测试，防作弊
  languageEntry:              # 语言不限时，每种语言各自的入口约定
    python: src/parking.py
    java:   src/main/java/Parking.java
    go:     src/parking.go

校验分三级，诊断而不是惩罚

级别典型情况处理
阻断 入口文件缺失 · 语法错误无法解析 · 提交了 forbidden 文件 无法执行评测。Verify 记 0，其余维度尽力评。 报告首屏直接给出诊断，让学员知道不是判低了而是根本没跑起来
警告 SPEC.md 原样交回模板 · transcript 过短 · 签名与约定不符 照常评测。对应维度自然拿低分，不额外惩罚—— 规则没写清本来就该 Spec 维度扣分，重复扣两次不合理
提示 未提交可选项（tests/、NOTES.md） 仅提示，不影响分数

设计原则：校验的作用是给出明确诊断，不是叠加惩罚。 学员最怕的是「我明明写了为什么 0 分」——校验报告要能一句话回答这个问题。

本地预检：push 之前自己先跑

starter 骨架里内置一个预检命令，学员随时可以自查，不用把提交次数浪费在格式问题上：

$ ./drill check

5.3 赛季积分制

赛季榜只有一个，不分蓝黄。但如果直接累加各场原始分，会出问题—— 强模型下同样的努力更容易拿高分，这会激励人挑蓝区场次打。

解法是赛季积分用场次百分位而非原始分：

场次积分 = round(100 × (1 − (本场名次 − 1) / 本场参赛数))
          第 1 名 100 分 · 中位数 50 分 · 末位 100/n 分

赛季总积分 = Σ 各场次积分        ← 榜单默认排序，奖励参与
场均积分   = 总积分 / 场次数      ← 并列展示，反映稳定水平

比的是你在本场（同区、同题、同模型）里的位置， 天然公平。个人赛的「本场名次」按同一道题的所有提交者排。

计入范围：只有 origin: official 的项目。 老员工众包发布的挑战题不进赛季总分——它们的分由出题人主观判定，宽严不一， 混进来会污染赛季榜的可比性。众包题走挑战榜，并且它的 Spec / Code / Collab 三个维度照常计入个人能力画像（这三项是自动评的、跨题型可比）。

这条设计的价值不只在蓝黄之间。 蓝区只有零星几场集中赛，「挑蓝区打」的空间本来就小。但即使全是黄区场次， 不同题目的难度也不一样——一道埋了六个澄清点的硬题，均分可能比基础题低二十分。 用原始分累加等于惩罚了参加硬题的人。场次百分位把题目难度差也一并消掉了。

06出题方法论

题目质量决定训战质量。这一节是可复用的出题方法，让部门任何一位资深工程师都能出出合格的题。

6.1 什么样的题适合训战

✓ 好题的五个特征

  • 无业务门槛：新人一听就懂，不需要背景知识
  • 边界密集：正常路径简单，边界条件多且刁
  • 口头描述必然遗漏：天然含有说不清的歧义
  • 可自动验收：对错由测试判定，不靠人评
  • 变更可自然引入：加一个维度就能打穿硬编码实现

✗ 不适合的题

  • 需要大量领域知识才能理解需求
  • 正确答案不唯一、只能人工判断优劣
  • 依赖外部服务、数据库、网络
  • 规模太大，限时内做不完主流程
  • 能在网上搜到现成实现

6.2 三档测试设计法

隐藏验收测试必须分档设计，这样一跑就能定位问题出在哪一层，而不只是给个总分。

档位建议题量权重设计要领
基础档8×1.0 需求原文明说的规则。要让大多数人满分——它的作用是制造「看起来没问题」的错觉
边界档6×2.0 需求没说但有工程直觉就该想到：零值、空值、阈值前后、极大值、非法输入
澄清档6×2.0 核心。答案无法从需求原文推导，只能靠提问获得。这一档是分水岭
变更档5×1.6 变更后的正确性 + 向后兼容回归（原有调用方式不能坏）

基础档满分而边界/澄清档大面积失分，是最有教学价值的结果形态： 代码看起来完全正常、跑一下也没问题，但三分之一的真实场景是错的。

6.3 澄清点设计法

澄清点是训战的灵魂。设计原则：这条规则必须有两种同样合理的理解，且需求原文无法判定选哪个。 四个可靠的套路：

套路模板例子
含不含等号「X 以内」到底含不含 X 本身「15 分钟以内免费」——正好 15 分钟免不免？
操作顺序两个操作都要做，先做哪个封顶和打折，先封顶还是先打折？结果差 12 元
词义边界一个日常词有多种技术含义「一天最多 60」——自然日还是滚动 24 小时？
作用范围某个约束作用于整体还是每个单元封顶是全局封一次，还是每个周期各封一次？

验证方法：出完题后，把口头需求原样丢给一个强模型，让它直接实现， 然后跑你设计的隐藏测试。如果它拿到 90 分以上，说明澄清点埋得不够；理想结果是 60–75 分—— 基础档全绿，边界与澄清档各挂一半。

6.4 出题清单

一道完整的题需要以下产出。语言不限的题目，带 ⚑ 的项要按每种语言各做一份：

产出物说明

README.md学员看到的题面：交付物、硬性要求、提交纪律

6.5 题库运营

两个区的题目消耗速度差很多。 蓝区只有集中限时赛——所有人同时开始、当场结束， 答案没有流传的时间窗，同一道题换一批人可以反复用。 黄区的赛季刷榜长期开放，才是题库消耗的主要来源。 下面的措施主要针对黄区。

开放窗口刷题会消耗题库。学员之间会传答案，一道题放三个月就废了。这是运营问题，不是技术问题：

  • 疲劳度追踪：平台记录每道题的使用次数与分数分布。当平均分显著上升而离散度下降， 通常意味着答案在流传，该退役了
  • 同批次分卷：同一批人发同类型的不同题，降低串题收益
  • 持续产出：建议每季度新增 3–5 道，由资深工程师轮值出题，出题本身也算训战贡献

6.6 众包出题：老员工发布挑战

这条机制的价值远大于「多一个题目来源」。

  • 题库可持续。开放刷题三个月就把题刷废了，靠管理员出题追不上消耗，众包才是唯一可持续的产出方式
  • 把老员工卷进来。真正需要转变 AI 协作习惯的其实是有经验的人——他们最容易「我自己写更快」。 让他们出题、看新人怎么用 AI 解自己的题，比给他们上课有效得多
  • 可能真的解决问题。如果题目来自在研难题，新人解出来的东西是能用的。 那就不只是「训」，是真的「战」

自动体检项

test 标准题

  • 四档测试齐全，各档题量在合理区间
  • 参考实现跑隐藏测试必须满分——不满分说明测试本身有 bug
  • 裸提示强模型基准分落在 60–75 区间：>75 说明澄清点埋得不够， <60 说明题太难或测试有问题
  • 多语言题：题号与档位跨语言严格一一对应
  • 澄清点 ≥ 4 个

bounty / explore 挑战题

  • 必填「什么算解决」的验收标准——没有它出题人自己也评不了
  • 使用真实代码时必须声明 requiredRepos
  • 敏感信息扫描：客户名、IP、密钥、工号、内部域名
  • 出题人承诺评审 SLA（建议 5 个工作日）
  • 悬赏额度与有效期

「裸提示强模型基准分落在 60–75」这一条是最有效的自动体检项—— 它用一次模型跑分就替代了大量人工判断，直接量化了这道题「埋得够不够深」。 体检报告一并展示给出题人，让他知道该往哪个方向补澄清点。

好题可以被采纳为官方题

众包题默认 origin: crowdsourced，不进赛季总分。 但如果一道题体检数据漂亮、实战区分度好（分数分布离散、澄清档确实拉开差距）， 管理员可以把它采纳为官方题，编排进下一场正式比赛——此时它就计入赛季总分了。

这条路径同时是给出题人的最高激励： 自己出的题被全部门正式比一场，比任何积分都有分量。也让「出好题」有了明确的目标—— 不是出得多，是出得准。

口头需求

「做个会员积分。消费 1 块钱得 1 分，普通会员 1 倍，银卡 1.5 倍，金卡 2 倍。 积分满 1000 升一级。积分一年过期。退货要把对应的积分扣回来。 给我个函数，输入消费记录列表，输出当前积分和等级。」

埋设的澄清点

编号问题标准答案
C1升级后，倍率是从下一笔开始生效，还是当笔就生效？下一笔生效
C2「积分满 1000 升一级」——是累计总积分还是当前余额？累计获得总积分，不因过期或退货回退等级
C3一年过期是按笔各自计时，还是按自然年统一清零？按笔，各自获得日起满 365 天过期
C4退货扣积分，按当时的倍率还是现在的倍率？按当时那笔的倍率原路扣回
C5退货时那笔积分已经过期了怎么办？不再扣减，已过期视为已消失
C6扣完变成负数怎么办？下限为 0，不允许负积分

变更包（第 60 分钟投放）

变更包 A · 默认

新增「积分抵扣现金」：100 积分抵 1 元，抵扣的积分按先进先出消耗； 被抵扣的积分不参与等级累计。函数加一个 redeem 参数，原有调用不能坏。

变更包 B · 进度快时用

新增「双倍积分日」：指定日期区间内倍率再翻倍，且该区间的积分有效期缩短为 90 天。 难度显著更高，需要重构积分批次模型。

为什么这题好：C4「按当时倍率还是现在倍率」几乎没有人会主动想到， 但它直接决定要不要为每笔积分保留获得时的快照——这是数据模型层面的决策，事后再改就是重构。 变更包 A 的 FIFO 消耗会打穿所有把积分当成单个数字而非批次列表的实现。

能力切面
「会不会给上下文」——真实工作里 90% 的时间是改代码，不是写新代码

题目形态

提供一个 450–600 行、无文档、命名混乱、测试覆盖约 50% 的限流器模块， 内含三种已实现策略（固定窗口、滑动窗口、令牌桶），其中滑动窗口有一处已知但未修复的精度问题。 要求新增「漏桶」策略，并且不能破坏任何现有行为。

刻意埋设的障碍

  • 策略注册逻辑分散在三处，只改一处会导致新策略静默不生效
  • 有一个看似废弃、实则被反射调用的方法，删了会挂
  • 配置项命名与实际语义不符（maxBurst 实际控制的是窗口长度）
  • 现有测试里有 2 个是长期 skip 的，取消 skip 会暴露既有缺陷

样题 C · 产出验证：绿灯下的陷阱两区皆可 团队 2 人 · 集中场次 90 分钟
考察
代码评审能力、写反例测试的能力、对 AI 产出的怀疑意识
能力切面
「会不会验」——这是最难教、也最少被训练的一项

题目形态

把角色反过来：不写代码，改做评审。给出 3 份 AI 生成的实现（同一道计费题）， 全部通过随题提供的 12 个公开测试。其中：

  • 1 份是正确的
  • 1 份有单一隐蔽缺陷（如浮点累加误差，只在特定金额组合下显现）
  • 1 份有双缺陷互相抵消——两个 bug 在公开测试的取值范围内恰好抵消， 单独修掉任何一个，原本通过的测试反而会挂

交付物与评分

交付物评分方式
缺陷报告找出的真缺陷数 − 误报数。定位到行号才计分
复现测试核心：提交的测试必须在缺陷实现上挂、在正确实现上过。 平台自动交叉验证，不靠人判
修复补丁修完必须 25 道隐藏测试全绿
评审记录与 AI 的对话：怎么用 AI 辅助找 bug，而不是让 AI 替你下结论

「双缺陷互相抵消」这一份是全题的题眼。 它精确演示了为什么抽查几个用例验证 AI 代码是不够的—— 现场把其中一个 bug 单独修掉、另一道原本通过的测试当场变红，这个瞬间比讲十遍都管用。

本题的评分不用标准四维度，改用专属权重：缺陷发现 35 · 复现测试 35 · 修复正确性 15 · 协作过程 15。 Schema 不变，只是 criteria 列表不同——这正是三维正交模型的好处。

黄区团队训战的第四个方向（建议后续补齐）：任务分解。 给 15 个文件做同一类改造（统一错误处理或日志格式），规模明显超出弱模型单次能力，必须拆解 + 设检查点 + 批量验证。 评分重点是完成率、15 个文件改法的一致性、有没有引入回归。这道题在黄区的教学价值最高， 因为它逼出的正是黄区 P3 那四个抽取项测的能力。

一期就要做对的三件事

  1. Schema 先定死。一期只填 Verify 和 Code 两个维度，但字段结构必须是完整版—— 二三期只是把空字段填上，而不是改结构。改 Schema 意味着历史成绩全部作废。
  2. rubricVersion 从第一天就带上。否则半年后没人说得清某个分数是按哪版判据算的。
  3. 幂等性一期就要验证。同一 commit 重跑必须同分，这是后面所有可比性的地基。

09风险与对策

风险影响对策
弱模型抽取准确率不达标高 二期设阅卷校准集：人工标注 20 份对话记录作金标准，跑内部模型看一致率。 ≥85% 则自动阅卷；80–85% 提高人工复核比例；<80% 该项降级为纯人工。 校准结果本身就是内部模型的能力证据
题库消耗，答案流传高 疲劳度追踪（均分上升 + 离散度下降即退役）、同批次分卷、每季度轮值出题 3–5 道
蓝区评测结果抖动中 强制结构化抽取（不许自由打分）+ 隐藏测试必须真跑（不许模型推断）+ 温度设 0。 定期用同一份提交做双盲重评，抖动 >2 分则复查评测指令
集中场次 CI 资源争抢中 并发上限 + 队列 + 场次前临时扩 runner。集中场次结果本就封存， 允许最慢一份延后几分钟，不影响揭晓
沙箱逃逸 / 恶意代码中 K8s Job：禁网、只读根、非 root、CPU/内存配额、硬超时；评测容器与平台服务网络隔离
团队项目搭便车中 强制角色分工（领航员 / 驾驶员，定时轮换）+ 团队页展示各成员 commit 贡献。 团队分不进个人口径，从机制上消除争议
判据被质疑不公平中 判据全文对学员公开（评分标准页），每分扣减附证据链与原文引用， source 字段标明是脚本/模型/人判的。开放申诉入口， 申诉本身也是训战素材
语言选择影响分数中 见 4.5：进入评分的指标必须跨语言可比或按参考实现归一化，不可比的只展示不计分。 每季度做一次分语言均分校验，偏差 >3 分则调整归一化基准
出题人评审拖延中 悬赏题的分全压在出题人身上，他不评就一直挂着。对策：发布时强制承诺 SLA、 超期自动提醒、连续超期暂停发布权；平台首页常驻「待你评审 N 份」提示
众包题质量参差中 自动体检卡住大部分问题（尤其「裸提示基准分 60–75」这一条），人工终审兜底； 上架后持续监控区分度，满分率过高或离散度过低即退役
真实代码越权访问中 题目必须声明 requiredRepos，终审时按需授权，参与者访问范围不扩大； 发布前自动扫描客户名、IP、密钥、工号
跨部门横向比较的敏感性中 榜单默认全域但支持按组织下钻，个人可切到「本级榜」降低压力； 部门级报表只对该节点管理员可见，不做跨兄弟部门的公开排名
组织调整导致历史数据错乱中 成绩快照里固化提交时的 orgPath，组织调整不追溯改写历史； 画像按「当时归属」统计，避免调岗后成绩凭空转移
新人挫败感低 首场明确定位为「暴露问题」而非考试；成绩页强调改进建议而非排名； 薄弱项直接推荐对应练习题
